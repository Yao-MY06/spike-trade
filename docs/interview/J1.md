# J1 秒杀可靠性主链 · 讲清题

## 1. 这是什么？

把原来的「Lua 扣 Redis 后直接发 MQ」改成可靠链路：Lua 成功后先把下单意图写进 MySQL 本地消息表（outbox），后台 relay 确认 RabbitMQ 收到后再标记已发送，消费者用一个事务完成订单落库和数据库库存扣减；对账任务定期比较 Redis、outbox、订单和数据库库存。

## 2. 为什么选本地消息表 + relay，而不是事务消息？

需求是保留现有 RabbitMQ，不更换 broker。RocketMQ 事务消息能缩小 W1 窗口，但需要引入新中间件；本地消息表能复用现有 MySQL，并给对账提供一份持久化的「预约意图」。代价是热路径多一次 INSERT、relay 有轮询延迟、必须做幂等；这些代价都在 spec 里明确接受，吞吐留给 J4 实测。

## 3. 具体流程是什么？

1. 入口先判空 `UserHolder`，避免先取 id 再判空。
2. `seckill.lua` 原子判断库存 key、重复预约、扣库存并写 zset（带时间戳）；缺库存 key 返回 3。
3. 生成订单号，写 `tb_seckill_outbox`（主键=订单号，`(user_id,voucher_id)` 唯一）。任何写库异常都执行幂等 `unreserve`。
4. relay 条件领取 `status=0` 且到期的行，发布时带 `message_id`、mandatory 和 `CorrelationData`；ack 且无 return 才标 SENT，否则退避重试。
5. Consumer 在独立事务 Bean 中先插订单再 `stock > 0` 扣库存。主键重复且同 id 已存在视为重复投递；唯一键冲突但 id 不存在、库存不足、非法 JSON 都抛不可重试异常进入 DLQ。
6. 对账 A-E：A 孤儿预约回滚；C 已发无单重发或终止；B 停滞待发、D 订单缺预约、E 库存漂移只报告。

## 4. 出错怎么兜底？

- Lua 成功但 outbox 写失败：请求线程立即 `ZREM + INCR`，失败则交给 A 类对账。
- broker 宕机：outbox 留在 NEW，relay 指数退避不放弃；恢复后补发。
- 重复投递：订单主键 + 用户券唯一索引 + outbox 唯一键三层幂等。
- 消费失败：可重试错误 3 次；耗尽或确定性错误由 recoverer 投递到 DLQ，消息头含异常信息。
- 消息已确认但无订单：C 类对账重发（上限 3）或标 DEAD。
- Redis 丢了预约：D 类报告；库存不一致：E 类报告，不自动重建 Redis。
- 残余风险：极慢请求可能在 A 类回滚后又写成功 outbox；此窗口没有强分布式事务，ADR 已写明。

## 5. 数据怎么测的？

- 纯 Mockito：入口判空/回滚、Handler 四种结果、relay ack/nack/return/异常、重试分类、A-E 对账。
- 真实 Redis：三个 Lua 的成功/不足/重复/缺 key/幂等/快照/200 并发。
- 真实 e2e：重复投递 5 次、broker 停机 3 单、孤儿预约、DLQ 两条、A-E 各一次、outbox 冲突回滚、N=3 M=5 并发。
- 全量 `mvn clean test` 34 个用例、package、Lua 与全部 e2e 的原始输出在 `evidence/J1/`；所有数字注明环境和来源。
