# J1 秒杀可靠性主链 · spec

> 模块号 J1　|　日期 2026-11-04　|　对应门：收缩门 ②（Lua → MQ → 落库）与 ③（幂等 + 失败恢复/对账）
> 本文回答「我想要做什么」；怎么做见 `plan.md`，顺序见 `task.md`，怎么检查见 `checklist.md`，取舍见 `adr-001-reliable-publish.md`。

## 1. 背景

基线（`docs/evidence/baseline/`）证明秒杀链路在单用户串行下能跑通，但 README 已知问题里有四条直接决定「会不会丢单、会不会重复单」：

| 编号 | 现状（有源码位置） | 后果 |
| --- | --- | --- |
| #1 | `seckill.lua` 只扣 Redis 库存并记用户；MQ 在 Java 侧 `VoucherOrderServiceImpl.seckillVoucher()` 发送，发送失败无任何补偿 | 券永久损失，用户之后也无法再抢 |
| #2 | `MQReceiver` 用 `count` 判重；`tb_voucher_order` 只有主键，无 `(user_id, voucher_id)` 唯一索引 | 并发重复消费可写出重复订单 |
| #3 | `MQReceiver` 的「已购」「库存不足」两个分支只 `log.error` 后 `return`，消息被确认后消失；抛异常时在 `default-requeue-rejected: true` 下会无限重投 | 无重试、无死信、无人知道 |
| #4 | `seckillVoucher()` 先 `UserHolder.getUser().getId()` 再判 `userId == null` | 判空无效，潜伏 NPE |

另有一条基线外的隐患：`seckill.lua` 在库存 key 不存在时 `tonumber(nil)` 直接报错（冷启动未预热）。

## 2. 目标

1. 下单成功返回订单号后，**订单最终一定落库**（只要 MySQL 与 RabbitMQ 最终可用）；不丢单。
2. 同一个用户对同一张券**最多一张订单**，任何重复投递、重复请求都不会写出第二张，也不会多扣一次库存。
3. 消息投递失败、消费失败**有处理路径**：可恢复的自动恢复，不可恢复的进入死信队列并可被发现。
4. Redis、消息表、订单表三份数据能被**对账**，发现的不一致能被报告，其中两类能自动修复。
5. 以上每条都有**实际制造故障**得到的原始证据（重复投递、broker 宕机、孤儿预约、消费失败）。

## 3. 功能需求

| 编号 | 需求 |
| --- | --- |
| FR1 | **资格判断（Lua）**：库存与「已预约」判断、扣减、记录在一个脚本内原子完成。返回 `0` 成功 / `1` 库存不足 / `2` 重复下单 / `3` 库存 key 不存在（未预热）。「已预约」记录带预约时间。 |
| FR2 | **本地消息表**：Lua 成功后，同一请求内向 `tb_seckill_outbox` 写一行（主键 = 订单号，`(user_id, voucher_id)` 唯一）。写入失败（含订单号生成失败）必须回滚 Redis 预约并向用户返回失败。 |
| FR3 | **可靠投递（relay）**：后台轮询未确认的消息，发布到 RabbitMQ 时开启 publisher confirm 与 mandatory；收到 ack 才标记已发送；nack、不可路由、连接失败、确认超时都会按指数退避重试，不设放弃上限。 |
| FR4 | **消费落库**：一个事务内「插入订单（主键 = 消息 ID）+ 扣减数据库库存（`stock > 0` 条件更新）」。同一条消息重复投递时不重复落库、不重复扣库存，并正常确认。 |
| FR5 | **失败分类**：可重试错误（数据库临时故障等）最多重试 3 次，退避递增；重试耗尽、或不可重试错误（库存不足、该用户已有另一订单、消息体非法）进入死信队列，并带异常信息。 |
| FR6 | **三方对账**：对单张秒杀券比较 Redis（库存、预约集合）、消息表、订单表，检查五类不一致（见 `plan.md` §5.4），自动修复「孤儿预约」与「已发送但无订单」两类，其余只报告。定时执行，也可用 HTTP 触发（默认关闭）。 |
| FR7 | **#4 修复**：未登录判空先于取用户 ID。 |
| FR8 | **可追踪**：订单号贯穿接口返回、消息表、消息头 `message_id`、日志、订单主键，一个订单号能串起整条链。 |

## 4. 非功能需求

- **一致性口径**：承诺「至少一次投递 + 消费端幂等」即最终一致；**不**宣称 exactly-once，也不宣称分布式事务。
- **兼容**：Java 8 目标、Spring Boot 2.3.12、RabbitMQ 3.8、MySQL 9.5、Redis 6.2；不引入新中间件。
- **安全**：凭据只来自 `config/application.yaml` / 环境变量，不进仓库；脚本与文档不写入任何密码。
- **可测**：每个故障场景有脚本，脚本产出的原始输出放进 `evidence/J1/`。
- **性能**：本模块**不做**性能结论。热路径新增一次 `INSERT`，其对吞吐的影响留给 J4 并发压测实测。

## 5. 不做的事

- 并发压测与吞吐/RT 数字（J4）；Docker Compose 与监控指标暴露（J2）；Gateway 与服务拆分（J3）；缓存击穿与分布式锁（J5）。
- 订单状态机、超时关单、支付、库存回补。
- **Redis 整体丢失后的重建**（只报告，不自动重建）。
- 多个 relay 实例并发运行的压测（SQL 层有条件更新抢占，但本模块不验证）。
- 消息表清理与归档。
- 对账接口的鉴权与限流（仅沿用现有登录拦截，且默认关闭）。
- 修改现有 `@RateLimiter` 限流行为（验证脚本通过清除限流 key 绕过，见 `plan.md` §8）。
- 已知问题 #5、#9–#12 等与秒杀可靠性无关的问题。
