# ADR-001　秒杀下单消息怎么可靠地发出去

- 状态：已采纳　|　日期：2026-11-04　|　所属模块：J1
- 一句话：**保留 RabbitMQ，用「本地消息表 + relay + publisher confirm」，靠对账补上 Lua 与消息表之间那个小窗口；不换 RocketMQ 事务消息。**

## 1. 要解决的问题

下单要同时做两件事：**① 在 Redis 里预约**（Lua：判库存、判重、扣减）；**② 让下游知道这个订单要落库**（发消息）。两件事不在同一个事务里，中间任何一点失败都会不一致：

| 窗口 | 发生什么 | 后果（基线现状） |
| --- | --- | --- |
| W1 | Lua 成功后、消息发出前进程崩溃或发送失败 | 库存被扣、用户被记为已购，但没有订单（已知问题 #1） |
| W2 | 消息发出了，broker 没收到（无确认） | 同 W1 |
| W3 | 消息被投递了两次 | 重复订单（已知问题 #2，无唯一索引） |

## 2. 备选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 本地消息表 + relay（采纳）** | Lua 成功后同请求写一行 outbox（MySQL）；后台 relay 轮询发送，收到 broker 确认才标记已发送；消费端幂等 | 不换 broker；每个预约意图在数据库里有**持久记录**，可审计、可对账；对任何 MQ 通用；broker 宕机时下单照常成功、恢复后自动补发 | 多一次数据库写；relay 有轮询延迟；至少一次投递必然产生重复，必须幂等；表会增长需要清理；**Lua 与 outbox 写入之间仍有极小窗口** |
| B. RocketMQ 事务消息 | 先发半消息，再执行本地事务（这里是执行 Lua），提交；broker 对未决半消息回查本地状态（回查 Redis 里预约是否存在） | **不需要消息表和 relay**；半消息先于 Lua，能关闭 W1；业务代码更少 | 要引入 RocketMQ（NameServer + Broker）并替换已有的 RabbitMQ 与基线证据；回查逻辑依赖 Redis 持久性；没有数据库里的「预约意图」记录，对账缺一方数据 |
| C. 沿用现状（Lua 后直接发，失败只记日志） | — | 零改动 | 即问题本身 |
| D. 回到 Redis Stream（Lua 内 `XADD`） | 扣库存与入队在同一个 Lua，天然原子 | 窗口最小，课程原版就是这么做的 | Stream 本身受 Redis 持久化限制（默认只开 RDB，进程被杀会丢未持久化的数据）；本 fork 已换成 RabbitMQ，换回等于重写消费端 |

## 3. 决策与理由

1. **不是因为事务消息做不到，而是取舍。** B 在 W1 上比 A 更强；选 A 的理由是**成本与对账**：不更换 broker（基线、Compose 计划、证据都建立在 RabbitMQ 上），并且 outbox 给了对账一份**数据库里的第三方数据**——没有它，「Redis 预约了但没订单」无法区分「还在途」和「丢了」。
2. **A 不能单独关闭 W1。** 它把 W2 和 W3 变成「可重试 + 可幂等」，但 Lua 成功后、outbox 写入前进程被杀，依然会留下「孤儿预约」。这个小窗口由**对账任务**兜底：预约记录带时间，超过宽限期（默认 30 秒）仍无消息表行、也无订单的预约，回滚库存与预约（`plan.md` §5.4 A 类）。
3. **幂等不靠一道门。** 消息 ID = 订单号：① 订单**主键**挡住同一条消息重投；② 订单上 `(user_id, voucher_id)` **唯一索引**挡住「不同消息、同一用户」；③ 消息表上同样的唯一索引在请求入口挡住重复请求。
4. **relay 不设放弃上限。** broker 宕机可能持续很久；放弃等于丢单。退避封顶 60 秒，靠 lease（领取时把下次重试时间推后 5 秒）避免确认未到时被同一实例重复领取。

## 4. 后果

- 好处：broker 宕机期间下单照常成功；恢复后自动补发；每个订单号可从消息表追到订单。
- 代价：热路径多一次 `INSERT`（对吞吐的影响在 J4 实测，**现在不下结论**）；订单号在返回给用户时订单**尚未落库**，是异步最终一致；消息表需要日后清理（本模块不做）。
- 已知残余风险 1：宽限期过短时，极慢的请求会被 A 类误判为孤儿并回滚预约；但该请求随后仍可能成功 INSERT outbox，形成「Redis 无预约、库有 outbox」的裂口。outbox 的 `(user_id, voucher_id)` 唯一索引只能挡住同一用户，不能挡住别的用户已经抢走库存。
- 已知残余风险 2：上述裂口下若别的用户抢走库存，原请求仍拿到订单号，消息最终进入死信；`INSERT` 已提交但客户端收到超时也同理。E 类无法识别这种「预约、outbox、订单」关系错位，只有 D 类（订单缺预约）能报告。
- 若以后要上 B：outbox 与 relay 可整体删除，消费端幂等与对账保留。
